# 트러블슈팅 로그

원인 파악에 시간이 걸렸던 에러·장애를 기록한다. 각 항목: 증상 → 원인 → 해결. 새 항목은 위에 추가.

## 4대 가치 항목별 조사 결과(fourValueItems)가 한 번도 생성되지 않음 (2026-09-02)

- **증상**: Ⅴ장 "[ ○○ 가치 조사 결과 ]" 박스가 항상 "정성 요약이 아직 없습니다"로 비어 있고,
  담당자가 매번 "AI 요약 생성" 버튼을 눌러야 했다. 로그에도 실패가 안 보인다.
- **원인**: `qualitative_section_analysis_runs.section_key`의 check 제약 목록에 `fourValueItems`가
  빠져 있었다. `runSectionAnalysesForReport`가 **작업 시작 이력을 먼저 insert**하는데 그 insert가
  제약 위반으로 던지고, 태스크의 try/catch가 그대로 삼켜서 **LLM 호출까지 가보지도 못하고**
  건너뛰어졌다. 실행 이력 테이블에도 흔적이 안 남아(시작 자체가 실패) 6번의 작업에서 다른 5개
  섹션은 6/6 성공, fourValueItems만 시도 기록 0건이었다.
- **해결**: 제약 목록에 `fourValueItems` 추가(`schema.sql`, `npm run db:migrate`) + **이력 기록
  훅을 `safely()`로 감싸 부수 작업 실패가 본 작업을 죽이지 못하게** 했다(`sectionAnalysis.ts`).
  섹션 키를 새로 추가할 때는 이 check 제약도 같이 넓힐 것 — 안 그러면 조용히 안 돌아간다.

## 2026-09-02 — 앵커 인용문 1건이 원문에서 복원되지 않음 (미해결 · 추적 중)

**증상**: 인용문을 원문 위치로 지목하게 하는 앵커 출력(`lib/pipeline/anchorQuotes.ts`)을 켜고
리바랩스 14문항을 돌린 결과, 인용문 **372개 중 371개(99.7%)** 가 원문에서 정확히 복원됐고
`'펫과의 산책' 기능 만족도` 문항에서 **44개 중 1개**만 복원되지 않았다. 나머지 13문항은 전량 복원.

**원인**: **아직 모른다.** 당시 로그가 `복원 34/34` 처럼 **개수만** 남겨서 어떤 앵커가 왜 실패했는지
알 수 없었다. 같은 문항을 그대로 다시 돌려 재현을 시도했으나 34/34로 성공해 **재현되지 않았다**
(모델 출력이 매번 달라 인용문 개수 자체가 44 → 34로 바뀐다). 즉 상시 결함이 아니라 **간헐적**이다.

가능한 원인은 셋뿐이고 코드상 그 외 경로가 없다:
- `no_source` — 모델이 입력에 없는 응답자 번호를 지목
- `from_missing` — 시작 조각을 원문과 다르게 적음(요약·오타)
- `to_missing` — 끝 조각이 시작 지점 **뒤에** 없음(앞쪽에만 있거나 다르게 적음)

**해결(부분)**: 원인 규명이 아니라 **다음 발생 때 즉시 알 수 있게** 만들었다. `resolveAnchorQuotes`가
실패마다 `{응답자 번호, from, to, 사유}` 를 반환하고 `fastReportAnalysis`가 경고 로그로 남긴다.
응답 원문은 남기지 않는다(개인정보) — 모델이 적은 짧은 조각만 남긴다.

**영향도**: 낮다. 앵커 이전 방식도 모델이 원문을 옮겨 적다 한 글자만 틀리면 그 인용문을 조용히
버렸다(`retainOnlyVerifiedQuotes`). 즉 **이 실패는 앵커가 새로 만든 문제가 아니라 원래 있던 것이고,
앵커 쪽은 최소한 사유가 로그에 남는다.** 인용문 하나가 빠져도 카테고리·건수·인사이트·극성은 그대로다.

**다음에 볼 것**: 경고 로그에서 사유 분포를 확인한다. `to_missing` 이 많으면 짧은 인용에서
from/to 가 겹치는 경계 처리(`slice()`의 `startsWith` 폴백)를 넓히면 되고, `from_missing` 이 많으면
프롬프트에서 "원문 그대로 옮겨 적을 것"을 더 분명히 해야 한다. `no_source` 는 응답자 번호 혼동이라
프롬프트 쪽 문제다.

## 2026-08-13 — 정성 분석 job이 "13/14 완료"에서 156분+ 멈춤 (에러 없이 무한 정지)

**증상**:
- ①(별도 건, 같은 세션) 정성 분석 중 "Failed to fetch" 빨간 에러 텍스트가 뜨며 2/14에서
  진행이 멈춤.
- ②(본 건) 진행률 13/14에서 156분 46초 동안 에러 없이 그냥 멈춰있음. 이후 자체적으로
  14/14(완료, 2개 실패)로 끝나긴 했지만 그 전까지 몇 시간 동안 사용자는 멈췄는지 진행
  중인지 알 방법이 없었음.

**원인 (두 가지, 서로 다른 위치)**:
1. **클라이언트: 폴링 워커가 네트워크 예외로 영구 종료됨.**
   `components/wizard/QualitativeStep.tsx`의 워커 3개가 `run-next`를 반복 호출(polling)하는
   `while` 루프에 `try/catch`가 없어서, 순간적인 네트워크 장애(fetch 예외) 한 번에 그 워커의
   루프가 통째로 끝나버림. 워커 3개가 하나씩 죽고 나면 서버 job은 계속 진행 가능한 상태인데도
   아무도 폴링하지 않아 화면이 "Failed to fetch"로 멈춘 것처럼 보임.
2. **서버: `recommendation.ts`/`summary.ts`가 타임아웃 가드 없는 raw Claude 호출을 씀.**
   이 프로젝트는 Claude 호출이 간헐적으로 멈추는 문제를 이미 겪어서 `lib/pipeline/
   claudeGuard.ts`(타임아웃+재시도 래퍼)를 표준으로 정해뒀는데, 나중에 추가된
   `lib/pipeline/recommendation.ts`(2026-07-30/08-03/08-13)와 `lib/pipeline/summary.ts`
   (2026-07-30)는 이 표준을 안 쓰고 `ai` 패키지의 raw `generateText()`를 직접 호출하고
   있었음(타임아웃·재시도·AbortController 전혀 없음). 이 두 파일은 마지막(14번째) 문항의
   Stage2가 끝나는 순간 `app/api/qualitative-jobs/[jobId]/run-next/route.ts`가 **같은 HTTP
   요청 안에서 동기로** 호출하는 "후처리 번들"(제언·결과요약 등)에 포함돼 있어서, 그 안의
   호출 하나가 멈추면 요청 자체가 영원히 응답하지 않음 — 아무것도 reject/timeout 되지 않으니
   클라이언트에도 잡을 에러가 없어 그냥 무한정 "13/14"에 멈춰 보인 것.

**해결**:
- (①) `QualitativeStep.tsx`의 워커 루프 안에 `try/catch` 추가: 실패해도 루프를 빠져나가지
  않고 2초 대기 후 재시도. 사용자 요청대로 재시도 횟수 대신 상태 문구
  ("네트워크가 불안정하여 연결을 재시도했고, 분석을 재개했습니다")를 `hadNetworkFailure`
  플래그로 노출, 성공하면 5초 후 자동으로 사라짐.
- (②) `recommendation.ts`·`summary.ts`의 raw `generateText` 호출 4곳(개발우선순위 본문/방향성,
  기능개선제안, 결과요약) 전부 `withClaudeGuard(label, () => streamPlainText({...,
  hardTimeoutMs: 120_000}, label), { onUsage })`로 교체 — 다른 파이프라인 파일들
  (`stage1.ts`/`stage2.ts`/`sectionAnalysis.ts`/`customerRecommendations.ts`)과 동일한
  120초 하드 타임아웃+재시도 보호를 받도록 통일. `npx tsc --noEmit`으로 컴파일 확인.

**앞으로의 동작**:
- 네트워크가 순간적으로 끊겨도 폴링 워커는 죽지 않고 계속 재시도하며, 화면엔 "재시도 중/
  재개했습니다" 상태 문구만 잠깐 보이고 자동으로 없어짐 — "Failed to fetch" 에러 텍스트는
  더 이상 뜨지 않음.
- 후처리 번들 안의 어떤 Claude 호출이 멈춰도 120초 안에 자체적으로 타임아웃되고 재시도(최대
  2회)되므로, "13/14에서 몇 시간째 정지"처럼 무한정 멈추는 상황 자체가 발생하지 않음. 개별
  job item은 여전히 `MAX_ITEM_ATTEMPTS=3` 재시도 후에도 실패하면 "일부 문항 실패"로 표시될
  수 있지만(정상적인 부분 실패), 전체 job이 응답 없이 멈추는 일은 없음.

**교훈**: 같은 "정성 분석이 멈춘다"는 증상이라도 원인이 클라이언트(폴링 루프 예외 처리 누락)와
서버(타임아웃 가드를 안 쓴 새 파일) 두 군데에 독립적으로 있었다. 새 파이프라인 파일을 추가할
때 `claudeGuard.ts`를 거치지 않고 `generateText`/`streamText`를 직접 부르면, 예전에 이미
고친 "Claude 호출이 멈추면 전체가 무한정 걸린다"는 버그가 그대로 재발한다 — 새 Claude 호출
코드를 작성/리뷰할 때마다 `withClaudeGuard`/`streamStructured`/`streamPlainText`를 쓰고
있는지 확인할 것.

## 2026-08-12 — 정성 분석 job이 "0/14 완료"로 17분+ 멈춤

**증상**: 정성 분석(고속 경로) job이 진행률 0/14에서 멈춘 채 17분 넘게 안 움직임. 결국 사용자가
job을 취소. 이후 재실행한 job도 2/14만 성공(`completed_with_failures`), 나머지는 실패.

**원인 조사 과정(처음엔 틀린 진단을 냈다가 실험으로 정정함)**:
1. 같은 날 커밋 `2a08c66`이 인용문마다 근거 부분을 추출해 볼드/밑줄로 표시하는
   `quoteEvidence`/`reasonSpan` 필드를 Stage2 스키마에 추가했다. 이게 출력량을 늘려 기존
   `120초 × 재시도 2회` 타임아웃(`withClaudeGuard` 기본값)을 반복적으로 넘긴 게 원인이라고
   1차 판단했다.
2. 사용자가 "이 볼드/밑줄 처리는 원래도 잘 나오던 거 아니냐"고 반박 — DB에서 job 이력을
   조회해 확인해보니, `2a08c66` **이전** job들은 전부 성공했지만 그건 애초에 reasonSpan
   필드 자체가 코드에 없던 시점이라 무관했고, `2a08c66` **이후** job은 성공한 적이 자체가
   없었다(사용자가 "잘 나왔다"고 본 화면은 오늘 2/14만 성공한 job의 그 2개 결과물이었다).
3. 그래도 "reasonSpan이 원인"이라는 결론이 맞는지 직접 실험으로 검증했다: 가장 오래 걸리는
   "개선아이디어" 문항에 대해 (a) reasonSpan 그대로, (b) 프롬프트 지시문만 제거, (c) 스키마에서
   필드 자체를 제거 — 3가지를 각각 단독 호출로 측정. 결과 109.0초/108.3초/113.4초로 **거의
   차이가 없었다**. reasonSpan은 지연의 원인이 아니었다 — 1차 진단은 틀렸다.
4. 진짜 원인은 별개였다: "개선아이디어" 문항 프롬프트가 소분류당 인용문을 "가능한 많이(2~6개),
   3개로 제한하지 말 것"이라고 지시해, 대분류 5~8개 × 소분류 2~4개 × 인용 최대 6개로 출력
   자체가 원래도 컸다(출력 토큰 8,000~8,800개). 이 문항이 108~113초대로 걸리는 게 기존
   120초 타임아웃 상한에 원래부터 아슬아슬하게 붙어 있었을 가능성이 높고, 여기에 워커
   3개가 동시에 다른 문항들을 호출하는 부하가 겹치면서 그날 유독 상한을 넘겼다고 추정된다.
5. 별도로, 큐 배정 순서 문제도 같이 있었다: `claimNextQualitativeJobItem`이 항상 stage1을
   stage2보다 먼저 배정해서, 어려운 문항 몇 개가 타임아웃으로 재시도를 반복하는 동안 이미
   stage1을 마치고 stage2만 남은(거의 끝난) 문항들이 워커(동시성 3)를 배정받지 못한 채
   무한정 대기했다 — "0/14에서 안 움직인다"는 증상의 직접 원인.

**해결**:
- `lib/pipeline/fastReportAnalysis.ts`: `withClaudeGuard`에 `maxAttempts: 1`을 넘기고
  `hardTimeoutMs`를 120,000×2회 → 200,000×1회로 바꿈(`streamStructured`가 지원하는 per-call
  override 추가). 같은 120초 창을 두 번 반복하는 것보다 한 번을 길게 주는 쪽이 실제 지연에
  더 잘 맞고, Vercel `maxDuration=300`(`run-next/route.ts`) 안에 여유가 남는다. 재시도 안전망은
  `withClaudeGuard` 내부가 아니라 job-item 단위 재시도(`MAX_ITEM_ATTEMPTS=3`,
  `lib/db/qualitativeJobs.ts`)가 대신 맡는다.
- `lib/db/qualitativeJobs.ts`의 `claimNextQualitativeJobItem`: 배정 순서를 `stage2` 우선(→
  `stage1`)으로 변경(`order by case phase when 'stage2' then 0 else 1 end, ...`). 어려운
  문항이 재시도를 반복해도 나머지 문항은 계속 끝까지 진행되고, 실패가 그 문항 몇 개로
  국한된다.
- `lib/pipeline/prompts.ts`의 `FAST_IMPROVEMENT_SYSTEM`: "개선아이디어" 문항의 인용 개수
  상한을 소분류당 2~6개("3개로 제한하지 말 것") → 2~3개로 줄여 출력량 자체를 낮춤. reasonSpan
  자체는 유지(3번 실험에서 지연 원인이 아님을 확인했고, 볼드/밑줄 강조는 검수 시간을 줄이는
  유의미한 기능이라 뺄 이유가 없음).
- **검증 완료(같은 날 2026-08-12)**: 위 수정을 반영한 뒤 실제 job을 처음부터 끝까지 재실행해
  14/14 성공(오류 0건, 855초/14분 15초)을 확인했다. 다만 예전 성공 실행(417.5초)보다는 여전히
  느리다 — 원인은 위 "정정" 항목 참고.

**교훈**: 사용자가 "확실하냐"고 반박했을 때 방어적으로 같은 주장을 반복하지 않고 직접 실험
(단독 호출 3회 비교)으로 검증한 게 잘못된 1차 진단을 바로잡았다. "그럴듯한 원인"(최근에 추가된
기능이 범인일 것 같다는 직관)과 "직접 측정으로 확인된 원인"은 다르다 — 특히 같은 커밋에
여러 변경이 섞여 있을 때는 개별 변경을 분리해서 측정하지 않으면 엉뚱한 변경을 범인으로
지목하기 쉽다.

**정정(같은 날, 이후 재조사)**: 위 3번 실험은 "개선아이디어" 문항 하나만 테스트해서 "reasonSpan은
지연 원인이 아니다"라고 일반화했는데, 이게 틀렸다. **표준 문항(기능/4대가치 등 13개)으로 다시
A/B 테스트하면 reasonSpan 있음 65.3초/55.7초, 없음 38.9초로 40~70% 더 걸린다** — 개선아이디어는
1회 호출로 끝나지만 표준 문항은 긍정·부정·중립 3개 그룹 전체에 reasonSpan을 만들어야 해서 부담이
훨씬 크다. **reasonSpan은 실제로 유의미한 속도 비용이 맞다** — 다만 이것만으로 "예전 성공 보고서
(417.5초, 문항당 90~113초)"와 "지금(855초, 문항당 115~223초)"의 전체 격차가 설명되진 않는다(그
보고서도 이미 reasonSpan 포함 상태였다 — reasonSpan은 이번 세션 이전부터 있었음, 이 세션에서
바꾼 건 타임아웃 설정과 개선아이디어 인용 상한뿐이라 둘 다 속도를 늦추는 방향이 아니다). 남은
격차는 코드 변경이 아니라 API 응답 속도의 날짜별 편차로 추정된다. reasonSpan을 뺄지는 속도와
인용 강조 품질의 트레이드오프라 사용자 확인이 필요한 제품 결정으로 남겨둠 — 임의로 빼지 말 것.

## 2026-08-12 — 정성 분석 14문항 전체 실패 (`No output generated`)

**증상**: 응답 내용 분석(정성 분석) 카드가 "14/14 문항 완료"인데도 전부 실패로 표시됨.
서버 로그: `AI_NoOutputGeneratedError: No output generated`, 그 직전
`AI_APICallError: Not Found (404)`, 요청 URL이 `http://127.0.0.1:8787/...`.

**원인**: `headroom`(로컬 캐싱 프록시 툴)을 설치하면서 `.zshrc`/`.bashrc`/`.profile`에
`export ANTHROPIC_BASE_URL="http://127.0.0.1:8787"`가 전역으로 추가됨(headroom은 `claude` CLI
호출을 이 프록시로 감싸 캐싱하려는 목적). `@ai-sdk/anthropic`의 기본 `anthropic` export는
`ANTHROPIC_BASE_URL` 환경변수를 자동으로 읽으므로, 이 프로젝트의 `npm run dev` 서버도 같은
셸(zsh)에서 실행되는 한 이 환경변수를 그대로 물려받아 모든 Claude API 호출이 실제 Anthropic
API가 아니라 headroom 프록시로 가서 404가 났다. 새 터미널을 열어도 재현됐던 이유는 이 export가
프로세스별이 아니라 셸 rc 파일(`.zshrc` 등) 자체에 있었기 때문.

**해결**: `lib/anthropic.ts`를 새로 만들어 `createAnthropic({ baseURL:
"https://api.anthropic.com/v1" })`로 baseURL을 코드에서 명시적으로 고정, 셸 환경변수와 무관하게
항상 실제 Anthropic API로 가게 했다. 기존에 `@ai-sdk/anthropic`에서 직접 `anthropic`을 import하던
13개 파일(`lib/pipeline/*.ts`, `lib/claudeQuant/analyze.ts`, `lib/productInfo/extract.ts`,
`app/api/chat/route.ts`, `app/api/report-workspace/*/route.ts`)을 전부 `@/lib/anthropic`에서
import하도록 교체.

**교훈**: 셸 rc 파일에 전역 env가 있으면 "새 터미널"도 근본 해결이 아니다. Node 프로세스가 읽는
프로바이더 기본 env(`ANTHROPIC_BASE_URL`, `ANTHROPIC_API_KEY` 등)는 로컬 개발 편의 도구(headroom
같은)가 조용히 가로챌 수 있으므로, 프로덕션 코드에서는 provider 생성 시 필요한 옵션을
명시적으로 고정해 셸 환경에 의존하지 않게 하는 편이 안전하다.
